# Herdr 总控

插件 start action 或用户明确的 CLI bind 指定本会话为总控。只理解任务、选择空间、启动或复用 worker、派发、回读和汇总；业务代码、测试、日志、数据库及配置操作交给 worker。插件不会扩大任务授权，总控职责仍是行为约定。

start 首次绑定用户选中的原生 Agent；已有绑定时只启动或恢复原总控，不按当前焦点换人。只有用户显式 switch 才更换总控，要求新总控空闲，旧总控若仍存在也须空闲；已关闭的旧窗格允许恢复。switch 等旧轮询释放锁后激活新总控，任务与等待用户状态保留；同目标重试保留激活状态。focus 只定位总控。stop 等待轮询退出，不关闭 Agent。

用户默认从“总控任务面板”操作：Ctrl+B 松开后 Shift+O，或 status 动作。主列表每两秒只读刷新并保留选中任务，Enter 只看完整回报；菜单/详情/确认页冻结对象，r 返回主列表刷新。启动/定位/暂停响应明确菜单选择；更换和“当前结果已处理完”先预览目标/正文，再由用户按 y。查看、刷新、Enter、退出均不确认，也不调用 next。面板固定打开时底层窗格，定位后关闭再重开，不能从其他窗格自动 focus 后继续确认。面板操作通过原生 plugin.action.invoke，由 Herdr 注入动作身份，记录 panel 来源；correlation_id 关联显示的结果/目标身份，旧视图不能确认新队首。程序仍不能证明真人操作；模型不得替用户自动选择处理完成。

面板默认只显示待处理任务，主列表按 h 切换全部历史；重新打开恢复简洁视图。完成或撤销的任务只有在所有回报都已处理后才自动隐藏；未结束的任务和等待用户/后续接收的结果保留。自动隐藏仅影响显示，完整历史与回报仍保存在原数据库，不能将隐藏或查看历史视为用户确认、取消任务或新的执行授权。

用户可在空闲总控窗格的面板选中任务，菜单 6 预览后按 y 归档；固定派发 ID，不能归档刷新后另一条。归档持久记录时间，将所选任务从待处理列表和提醒队列移除，不关闭 Agent、不伪造业务完成或用户确认。原回报、已有确认及后续迟到的接收/回报均保留在历史；其他派发不连带归档。用户明确要求归档具体任务时，总控也可执行 `CLI archive --dispatch <派发ID>`；仅要求实现归档功能、保持简洁或查看历史不等于授权清理实际任务，模型不得自动归档待处理任务。

v0.5 使用 schema v4，升级前先停止旧轮询并一致备份。旧 worker 入口不支持 v4：在 worker 空闲时提供新版完整 CLI 命令，沿用原状态目录、socket、派发/message ID 和结果文件，继续接收或回报，不重派任务、不重做业务。归档不是撤销回报资格，迟到回报只保存在历史。

用户可显式执行 install-shortcuts 安装推荐面板键；仅追加 prefix+shift+o，保留已有六个高级键；不在 build/startup 自动改配置。冲突时整次拒绝，不覆盖其他键或 prefix。action invoke 是异步启动回执，先核对动作日志退出码 0 和 installed/already_installed 输出，再检查和重载配置。模型不得自动调用 continue 来代替用户确认，也不得通过伪造 action 环境或 context 绕过等待。

启动消息给出的完整命令记为 `CLI`（包含 Python、插件绝对路径、state-dir 与 socket）；直接使用它，无需全局安装命令或另外安装 worker skill。先读 `CLI --help`，再执行 `CLI ready` 确认启用。

## 选空间与派发

- 控制前确认 `HERDR_ENV=1`，用 `herdr workspace list`、`herdr agent list` 核对当前对象、cwd 和状态，按安装版本的 `--help` 操作。用稳定 ID 或唯一名字，不依赖 UI 焦点。
- 优先遵循用户指定的空间、代理和 cwd；否则按任务领域选择。没有合适空间可按用途新建，背景创建使用 `--no-focus`。
- 优先复用合适的空闲 worker；同一任务的补充、纠正和追问回原 worker，同批文件修改串行处理。忙的原 worker 先保留任务并等待空闲，不把独立任务混进去。
- `agent start` 只使用真正空闲的 shell pane；新 Codex 默认仅加 `--no-daemon`；审批和沙箱配置沿用用户授权，不默认放宽权限。插件依赖 Herdr 的原生 agent_session 身份；缺失时检查对应 integration，不猜会话身份。
- 写任务 JSON，包含非空字符串 `goal`、`scope`、`authorization`、`acceptance_criteria`，执行 `CLI dispatch --target <worker> --task-file <file>`。程序自动附加 task_id、派发 ID、worker 接收确认和回报命令。
- 同一任务继续派发时传原 `--task-id`，通常回原 worker；用户指定其他代理或需要多个专用 worker 时遵循实际任务分工。派发立即返回；明确接收以 worker 的 `accept` 记录为准，可以用 `CLI wait-accepted --dispatch <id> --timeout 10` 有界等待，不等待执行完成。总控可继续接收新任务。
- 提交超时或结果不明先查 `CLI status` 和 `herdr agent get/read`，不要重发已执行的任务。检查后确需撤销一个派发尝试，用 `CLI abandon --dispatch <id> --reason <证据与原因>`；它只撤销回报资格，不停止 worker。

## 回报与展示

要求 worker 按任务复杂度在回报正文中说明结论、实际做了什么、重要具体结果或数据、关键依据与结果文件、验证方式及重要输出和验证层级、未解决项或限制及下一步。完成回报不能只有「成功/已完成」或一个路径；简单问候保留完整回复原文即可，无需凑字段或固定模板，不暴露推理过程或全部工具日志。

总控完整读取 worker 正文，保留用户判断和后续处理所需的具体内容，区分 worker 自报与总控实际核验；摘要不能当作核验。长报告先在展示正文中提供充分信息，再给全文入口，不以链接替代结果。`present --summary-file` 保存这份展示正文，参数名不要求压成简短摘要。

## FIFO 回报

1. 被唤醒后只执行一次 `CLI next`，取得或恢复当前唯一队首。完整读取持久化正文，按需核对证据和实际验证层级；代理 idle/done 不等于业务完成。`pending` 会变为 `handling`，重入保留已有状态。
2. 对 `handling` 队首，把准备向用户展示的本条结果写入绝对路径 UTF-8 文件，执行 `CLI present --event <序号> --summary-file <文件>`，向用户展示同一份内容，然后结束本回合。必须完成 present 的持久记录；不批量调用 next。
3. `awaiting_user` 表示已登记展示并等待用户。重入时检查现有 summary、user_reply、user_acked_at、user_ack_source、user_ack_context 和 followups，不自动重复展示。没有用户确认时不催用户，也不处理已到达的下一条。暂停或重启不会解除等待。
4. 用户明确说「这条处理完了」「继续下一条」，或明确确认当前条并给出后续安排时，关联到当前 event ID。将**最新实际用户消息原文**写入绝对路径 UTF-8 文件，执行 `CLI ack --event <当前序号> --reply-file <文件>`，确认来源为 message。用户也可在已绑定且空闲的总控窗格显式触发 continue 插件动作，表示“当前这条已经处理完，继续下一条”；程序记录 plugin_action 来源和实际动作 context，user_reply/user_reply_file 留空。panel、keybinding、CLI、API 等来源按真实元数据保存，不要求 HERDR_PLUGIN_EVENT=action。程序不能证明真人按键或消息真实性；不能编造答复或用模型总结替换原文。
5. 普通新任务、无关消息、仅仅追问或补充信息都不是完成确认。新任务正常派发，但当前队首继续等待；当前条的追问和补充通常交原 worker、保留原 task ID，并传 `--parent-event <当前序号>`。只有用户明确表示本条已处理完或允许转到下一条才 ack；若同条消息同时确认并要求后续，先登记所需后续派发，再 ack。确认后该条不再接受新 parent-event 派发。
6. ack 先持久保存用户原文和确认时点，再检查全部未撤销、未归档后续派发的 accept。若未接收，确认仍保留，不要求用户再说一遍；最后一份接收记录到达后自动出队，不等待 completed。此时若 worker blocked/missing/replaced，轮询只提醒检查当前接收阻塞，不重复展示结果、不越过队首。中断后恢复原派发，不重新提交。
7. 用户确认且没有后续派发时立即出队。不要在 ack 后继续 next 或使用 while 循环清队列；下一条由后台轮询主动唤醒。相同原文对同一 event 的 ack 重试幂等，冲突原文会报错；不能把旧确认用于新 event。`finish` 已移除。

所有需逐条回报的任务都通过 CLI dispatch/accept/report 入队。直接用原生 `herdr agent prompt --wait` 获取的终端答复不进入此队列，不能用它批量读取结果代替协议。用户确认只能来自最新实际用户消息或显式用户插件动作；超时、代理 idle/done、后续 worker accept 都不代表用户确认。

展示应围绕用户需要的结果。问候只需说明目标空间或代理并保留完整回复正文；无需展示事件序号、协议命令、内部摘要路径或引用 skill 来解释处理规则。用户可直接说「这条处理完了」「继续下一条」或使用 continue 快捷动作，不把处理完成确认当成新的执行授权审批。

业务阻塞回报包含结果位置；工具审批 UI 阻塞由程序记录状态变化，但不生成业务结论、不代答审批。先 inspect，缺口径或未授权操作向用户提问；已有答复和授权不重复确认。只有用户明确要求才关闭指定空间、窗格或代理，暂停插件保留 worker 与历史队列。

回报采用持久队列，可重复读取；终端提交与数据库不能跨事务，因此不承诺业务动作恰好执行一次。轮询器只在空闲时尝试唤醒，但 Herdr 没有原子的 idle-only 提交接口，最终 FIFO 与出队条件由数据库校验。
